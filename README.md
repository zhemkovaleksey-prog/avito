# Кандидатогенерация для поиска услуг Авито

Задача: для каждого поискового запроса отобрать из корпуса (189 212 объявлений) до 50 кандидатов так,
чтобы в них попало объявление, выбранное пользователем. Метрика — **Recall@50**.

Пошаговый разбор с кодом, анализом данных и ошибок — в **`solution.ipynb`**.

## Результат на локальной валидации

| Подход | Recall@50 |
|---|---|
| BM25 по всему корпусу (без учёта локации) | 0.406 |
| BM25 + фильтр по локации | 0.785 |
| Полнота пула кандидатов (верхняя граница) | 0.955 |
| **Итоговое решение: гибридный пул + LightGBM** | **0.907** |

Валидация: 3 355 отложенных запросов из train, их нет в обучении (подробности ниже). Обучение — на всём
train (497 673 пары).

## Как запустить

```bash
pip install -r requirements.txt          # Python 3.11
# положить train.parquet, benchmark_items.parquet, benchmark_queries.parquet в data/
python run_pipeline.py --data_dir data --out answer.csv
```

или выполнить `solution.ipynb` сверху вниз. Оба варианта дают один и тот же `answer.csv`:
готовят данные, прогоняют валидацию (Recall@50 бейзлайнов и решения), обучают ранкер,
строят ответ и проверяют его формат.

* Время — около 25 минут на 2 CPU, память — до ~5 ГБ.
* Каждый этап сохраняется в `cache/`: если запуск прервался, повторный запуск продолжит с места остановки.
  Кэш сам сбрасывается при изменении файлов данных; после изменения кода удалите `cache/` вручную.
* Внешних API нет, все случайности зафиксированы (`seed=42`, `deterministic=True` в LightGBM).
  Проверено: два запуска с нуля дают побайтно одинаковый `answer.csv`.

## Что нашлось в данных и как это повлияло на решение

1. **Локация — главный фильтр.** В 83% пар город объявления совпадает с городом поиска.
   В остальных случаях поиск шёл по региону или «по всей России» (например, из `107620` 61% выборов
   уходит в `637640`) либо был выбран соседний город.
   Поэтому разрешённые локации = своя + куда реально уходят пользователи из этой локации (по train)
   + соседние в радиусе 60 км. Плюс небольшой глобальный источник без фильтра.
2. **Запоминание объявлений почти не помогает.** Только ~10% объявлений корпуса встречаются в train,
   поэтому нужно сопоставлять **смысл текста**, а не запоминать пары (запрос, id).
3. **Фильтры в параметрах запроса надёжны.** При фильтре «Вид услуги X» у выбранного объявления
   тот же вид услуги в 98% случаев. «Тип услуги» совпадает в 83%, «Рейтинг 4+» соблюдён в 99%.
4. **Бенчмарк отличается от train по распределению.** Запросы в нём длиннее (3.2 слова против 2.45),
   и только 37% их текстов встречались в train. Валидация построена с учётом этого (см. ниже).

## Архитектура

```
запрос ──► нормализация + лемматизация (pymorphy3)
   │
   ├─ разрешённые локации: своя ∪ переходы из train (≥1%) ∪ радиус 60 км
   │
   ├─ источники кандидатов (топ-N из каждого, внутри разрешённых локаций):
   │    • BM25 по заголовку                                    150
   │    • BM25 по заголовку×2 + параметрам + описанию          150
   │    • TF-IDF по символьным 3–4-граммам заголовка           100
   │    • расширение запроса: похожие запросы из train → слова
   │      заголовков выбранных по ним объявлений → BM25        150
   │    • P(подкатегория | текст запроса), SGD-логрег на TF-IDF 100
   │    • «память»: объявления, выбранные по похожим запросам   30
   │    • глобально (весь корпус): BM25 60 + расширение 40
   │
   ├─ пул ≈ 410 кандидатов на запрос (полнота 0.955)
   │
   └─ LightGBM LambdaRank (30 признаков) ──► топ-50
```

**Почему так.** У кандидатогенерации две цели: полнота и скорость. Разные источники ошибаются
по-разному. BM25 точен на точных совпадениях слов. Символьные n-граммы ловят опечатки и словоформы.
Расширение запроса и классификатор подкатегории закрывают разрыв словаря
(«наращивание ногтей» ↔ «Маникюр, педикюр»): эти связи выучены из поведения пользователей в train.
Объединение источников даёт пул с полнотой 0.955. Выбрать из ~400 кандидатов 50 по 30 признакам — задача
обучаемого ранкера: вклад признаков нелинейный (например, соседний город уместен только при очень
хорошем совпадении текста), и подбирать веса вручную хуже.

**Признаки ранкера:** скоры всех источников (сырые и нормированные на максимум по запросу),
вероятность и ранг подкатегории, совпадение локации, P(локация объявления | локация поиска),
расстояние в км, «размытость» локации поиска, совпадение вида/типа услуги с фильтром, фильтр
рейтинга, рейтинг, число отзывов, популярность объявления и подкатегории, длина запроса.
Самые важные по gain: нормированный BM25 по полному тексту (29%), нормированный скор расширения (14%),
P(локация объявления | локация поиска) (13%), расстояние (9%).

## Валидация

Качество проверялось по схеме, которая имитирует бенчмарк:

* отложенные запросы выбираются равномерно по **уникальным текстам** (как в бенчмарке, средняя
  длина ~3 слова), по одной группе (текст, локация, фильтры) на текст, всего 10 000;
* для 63% из них из обучения удаляются **все** строки с этим текстом (новый запрос),
  для 37% — только сама группа: именно такая доля текстов бенчмарка встречалась в train
  (доля считается по данным, а не задаётся вручную);
* все статистики (классификатор, переходы локаций, расширение запроса) учатся только на оставшемся
  train, поэтому утечки нет;
* корпус для валидации = корпус бенчмарка + релевантные объявления отложенных запросов;
* отложенные запросы делятся на обучение ранкера (2/3) и валидацию (1/3). Ранняя остановка ранкера
  делается на части обучающих запросов, валидация в обучении не участвует.

Ограничение: число «конкурентов» у валидационных запросов в корпусе может отличаться от бенчмарка,
поэтому метрика на платформе может оказаться другой. Сравнение вариантов между собой при этом корректно.

## Разбор ошибок (валидация, 3 355 запросов)

| Тип | Доля релевантных | Пример | Что сделано |
|---|---|---|---|
| Нужная локация не попала в фильтр | 7.8% в первой версии | «укладка плитки» — объявление из соседнего города в 25 км | радиус 60 км + переходы локаций + глобальный источник: полнота пула 0.906 → 0.955 |
| В пуле, но ниже 50-го места | 4.9% | «няня в семью» → «Няня гувернантка» (ранг 100 среди десятков нянь) | неоднозначность: подходящих объявлений больше 50, наш топ-1 тоже релевантен |
| Нет общих слов с запросом | часть из 4.5% вне пула | «наращивание ногтей» → «Маникюр, педикюр», «джисиби» → «JCB 3CX» | классификатор подкатегории + расширение запроса по train |
| Слишком общий заголовок у выбранного объявления | часть из 4.5% вне пула | «ремонт кухонного гарнитура» → «Мастер на час» | частично закрывает категорийный источник |
| Шум в разметке | единичные случаи | «фотосессия с машиной» → «Водитель, встреча с табличкой» | не исправить |

Хуже всего работают запросы из одного слова (Recall@50 = 0.82): они самые неоднозначные.

## Структура

```
solution.ipynb       — пошаговое решение: данные, анализ, валидация, ранкер, ошибки, ответ
run_pipeline.py      — тот же пайплайн одной командой
src/pipeline.py      — этапы решения с сохранением результатов в cache/
src/data.py          — загрузка, лемматизация, разбор параметров
src/textproc.py      — нормализация и лемматизация текста
src/params.py        — разбор «Вид услуги / Тип услуги / Рейтинг» из параметров
src/split.py         — схема валидации
src/retriever.py     — источники кандидатов и признаки
src/ranker.py        — LightGBM LambdaRank, top-k, Recall@K
answer.csv           — отправленный ответ
validation_report.json — метрики валидации и важность признаков
```

## Использованные open-source библиотеки

pandas, pyarrow, numpy, scipy, scikit-learn (TF-IDF, CountVectorizer, SGDClassifier), LightGBM,
pymorphy3 (лемматизация). BM25 реализован вручную на разреженных матрицах. Предобученные нейросети
не использовались. Следующий шаг для улучшения — добавить источник на текстовых эмбеддингах
(например, `intfloat/multilingual-e5-small` + ANN-индекс) как ещё один генератор кандидатов и признак.
